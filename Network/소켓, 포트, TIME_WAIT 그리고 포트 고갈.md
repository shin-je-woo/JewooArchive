# 소켓부터 포트 고갈까지 정리

- 이 문서는 소켓과 포트 개념을 먼저 잡고, Keep-Alive, 커넥션 풀링, TIME_WAIT, 포트 고갈로 이어지도록 구성되어 있다.

## 1) 소켓이란 무엇인가

- 소켓은 애플리케이션이 OS의 네트워크 기능을 사용하기 위해 만드는 통신 객체이다.
- 애플리케이션은 네트워크를 직접 구현하지 않고, 소켓 API를 통해 OS 커널(TCP/IP 스택)에 요청한다.
- 실제로 TCP 연결 수립, 재전송, ACK 처리, 혼잡 제어 같은 동작은 커널이 수행한다.

## 2) 애플리케이션과 소켓은 어떻게 연결되는가

- 애플리케이션이 `socket()`을 호출하면 커널이 소켓(커널 객체)을 생성한다.
- 애플리케이션은 커널이 돌려준 파일 디스크립터(FD)를 통해 소켓을 참조한다.
- 프로세스는 자신의 FD 테이블을 가지고 있고, FD는 커널 소켓 객체에 매핑된다.
- 정리하면, 애플리케이션(프로세스) → FD(핸들) → 커널 소켓 객체 → TCP/IP 스택

## 3) 서버 소켓과 클라이언트 소켓의 차이

- 소켓은 서버용/클라이언트용으로 종류가 나뉘는 게 아니라 같은 소켓 API를 쓰되, 어떤 호출 흐름을 타느냐에 따라 서버 역할/클라이언트 역할로 동작한다.

### 3.1) 서버 역할일 때 (listen + accept)

- 서버는 보통 두 종류의 소켓을 사용한다.
- 리스닝 소켓(listening socket)
  - 역할: 특정 포트로 들어오는 연결 요청을 받기 위해 대기하는 소켓
  - 생성 흐름: `socket()` → `bind(서버IP:포트)` → `listen()`
  - 예: `0.0.0.0:80`, `서버IP:19024`
  - 특징: 데이터 통신을 직접 많이 하지 않고, 새 연결을 받아들이는 입구 역할이다.

- 연결 소켓(accepted/connected socket)
  - 역할: 특정 클라이언트 1명과 실제 데이터를 주고받는 소켓
  - 생성 흐름: 클라이언트가 접속하면 서버가 `accept()`를 호출할 때마다 새로 생성됨
  - 연결 소켓이 가지는 정보(개념): `서버IP:서버Port` ↔ `클라이언트IP:클라이언트Port`
  - 특징: 서버는 포트 하나로 listen하지만, 실제 통신은 연결마다 생성된 연결 소켓으로 수행된다.

### 3.2) 클라이언트 역할일 때 (connect)

- 클라이언트는 보통 다음 흐름으로 동작한다.
  - `socket()` 생성
  - `connect(목적지IP:목적지Port)` 호출
    - 이 시점에 OS가 로컬 임시 포트를 자동 할당(자동 bind)하는 경우가 일반적이다.
  - 이후 해당 소켓으로 read/write 수행

### 3.3) 요약

- 서버: `listen`으로 문(리스닝 소켓)을 열고, `accept`로 손님별 통화채널(연결 소켓)을 만든다.
- 클라이언트: `connect`로 서버의 문에 연결을 걸고, 생성된 연결로 데이터를 주고받는다.

## 4) 포트는 무엇이고 왜 필요한가

- 포트는 네트워크에서 호스트 내부의 통신 대상을 구분하기 위한 번호이다.
- 포트는 애플리케이션 그 자체가 아니라, 트래픽을 적절한 소켓으로 분배하기 위한 식별자이다.
- 실무에서 포트가 곧 서비스처럼 말하는 건 관용적 표현에 가깝다.
    - 특정 서비스가 특정 포트로 listen하는 경우가 많기 때문에 편의상 그렇게 말한다.
    - 하지만 하나의 애플리케이션이 여러 포트를 열 수도 있고, 같은 포트를 여러 프로세스가 공유하는 경우도 있을 수 있다.

## 5) 출발지 포트(임시 포트)가 매번 달라지는 이유

- TCP 연결은 보통 다음 4개 값 조합(4-튜플)로 구분된다.
    - 출발지 IP
    - 출발지 포트
    - 목적지 IP
    - 목적지 포트
- 서버 포트(목적지 포트)는 고정인 경우가 많다.
    - 예: 마이크로서비스가 19024로 listen
- 클라이언트가 같은 서버로 동시에 여러 연결을 만들려면 4-튜플이 서로 달라야 하고, 이때 주로 **출발지 포트가 달라진다.**

## 6) 임시 포트는 누가 정하고, 응답은 어떻게 돌아오는가

- 임시 포트는 대부분 애플리케이션이 직접 지정하지 않고 OS가 자동으로 할당한다.
    - 클라이언트가 `connect()`를 호출하는 시점에 커널이 사용 가능한 포트를 골라 자동으로 bind한다.
- 응답은 서버가 출발지 포트를 추측해서 보내는 것이 아니다.
    - 요청 패킷의 TCP 헤더에 이미 출발지 포트가 들어 있다.
    - 서버는 그 값을 그대로 응답의 목적지 포트로 사용한다.
- 예시
    - 요청: `클라IP:50123 → 서버IP:19024`
    - 응답: `서버IP:19024 → 클라IP:50123`
- 커널은 들어오는 패킷을 5-tuple(프로토콜 포함)로 매칭해 해당 소켓으로 분배한다.

## 7) Keep-Alive와 커넥션 풀링이 무엇인가

- Keep-Alive는 요청 하나가 끝났다고 TCP 연결을 바로 끊지 않고, 같은 연결을 유지해 재사용하는 방식이다.
- 커넥션 풀링은 여러 TCP 연결(소켓)을 미리 만들거나 유지해두고 필요할 때 꺼내 쓰고 반납하는 방식이다.
- 둘의 공통 목적은 다음과 같다.
    - 새 연결(connect, 3-way handshake)을 자주 만들지 않기
    - 연결 생성 비용과 패킷 오버헤드 줄이기
    - 지연과 변동성 감소

## 8) TIME_WAIT이 왜 생기고 어떤 의미가 있는가

- TCP 연결을 닫을 때, 특정 종료 흐름을 수행한 쪽(일반적으로 active close 쪽)이 TIME_WAIT 상태를 일정 시간 유지하는 경우가 많다.
- TIME_WAIT은 다음을 위한 안전장치 성격이 있다.
    - 지연 도착한 패킷이 다음 연결과 섞이는 것을 방지
    - 마지막 ACK 유실 시 재전송되는 FIN에 대응

## 9) 포트 고갈이 왜 발생하는가

- 포트 고갈은 클라이언트 역할을 하는 쪽에서 잘 나타난다.
- 요청마다 새 TCP 연결을 만들고 바로 끊는 패턴이 반복되면 매 연결마다 임시 포트를 하나 소비하고 종료된 포트가 TIME_WAIT으로 잠시 재사용이 제한되면서 사용 가능한 임시 포트 풀이 빠르게 소모될 수 있다.
- 특히 다음 조건이 겹치면 위험해진다.
    - 목적지 IP와 목적지 포트가 사실상 고정
    - 출발지 IP도 고정
    - 연결 생성 수(CPS)가 매우 높음
- 이 경우 4-튜플에서 사실상 변하는 값이 출발지 포트뿐이라, 고갈이 빠르게 올 수 있다.

## 10) Keep-Alive 및 풀링이 포트 고갈을 어떻게 완화하는가

- Keep-Alive/풀링을 쓰면 새 연결을 만드는 빈도 자체가 크게 줄어든다.
    - 요청이 많아도 연결 수는 제한된 개수로 유지된다.
    - 임시 포트를 새로 소비하는 속도가 느려진다.
    - TIME_WAIT로 쌓이는 포트 수도 줄어든다.
- 비교 예시(개념)
    - Keep-Alive 없음: 요청 10,000개 = 연결 10,000개 = 임시 포트 10,000개 소비 가능
    - 풀링 사용: 요청 10,000개 = 연결 100개 유지 = 임시 포트도 100개 수준에서 안정

## 11) 결론 정리

- 소켓은 애플리케이션이 OS 네트워크 스택을 사용하는 통신 객체이다.
- 서버는 고정 포트로 listen하고, 연결마다 accept 소켓이 생성된다.
- 클라이언트는 connect 시 OS가 임시 포트를 자동 할당해 연결을 구분한다.
- Keep-Alive/풀링이 없으면 짧은 연결이 폭증하고 TIME_WAIT이 쌓여 임시 포트 고갈로 이어질 수 있다.
- Keep-Alive/풀링은 연결 재사용으로 새 연결 생성을 줄여 포트 고갈을 상당 부분 완화한다.
