# 웹훅 보안과 서명 검증 이해하기

실무에서는 다양한 외부 시스템과 연동하기 위해 웹훅을 자주 사용한다.

처음에는 단순히 특정 이벤트가 발생했을 때 HTTP 요청을 받는 구조처럼 보이지만, 실제로 운영 환경에서 사용하려면 생각보다 고려해야 할 점이 많다.

대표적으로 요청이 정말 신뢰할 수 있는 발신자로부터 온 것인지, 중복 요청은 어떻게 처리할 것인지, IP 검증만으로 충분한지 같은 문제가 있다.

이 문서에서는 웹훅을 사용할 때 알아야 할 보안과 처리 관점의 핵심 개념을 정리한다.

## 1. 비대칭 암호화의 두 가지 큰 목적

비대칭키는 공개키와 개인키 한 쌍을 사용한다. 이 구조는 크게 두 가지 목적에 쓰인다.

### 1) 메시지 기밀성 보장

메시지를 제3자가 읽지 못하게 하는 목적이다.

동작 방식은 다음과 같다.

1. 수신자가 자신의 공개키를 공개한다.
2. 송신자가 그 공개키로 메시지를 암호화한다.
3. 수신자만 자신의 개인키로 복호화할 수 있다.

즉, 공개키로 암호화하고 개인키로 복호화한다.

### 2) 보낸 사람 신원 증명

이 메시지가 정말 특정 송신자가 보낸 것인지 확인하는 목적이다.

이 경우는 보통 개인키로 암호화하고 공개키로 복호화한다고 단순하게 설명되곤 하지만, 실제로는 전자서명이라고 보는 편이 정확하다.

실제 과정은 다음과 같다.

1. 메시지의 해시를 구한다.
2. 그 해시에 대해 송신자의 개인키로 서명한다.
3. 수신자는 송신자의 공개키로 서명을 검증한다.

따라서 정확한 표현은 다음과 같다.

- 기밀성: 공개키로 암호화, 개인키로 복호화
- 인증과 무결성: 개인키로 서명, 공개키로 검증

## 2. 전자서명은 왜 공개키로 검증할 수 있을까

핵심은 공개키와 개인키가 수학적으로 연결된 한 쌍이라는 점이다.

- 개인키는 서명을 생성할 수 있다.
- 공개키는 그 서명이 올바른 개인키로 만들어졌는지 검증할 수 있다.

여기서 중요한 점은, 공개키로 원문을 복원해서 읽는다는 느낌보다는, 서명이 유효한지 수학적으로 검사한다는 느낌에 가깝다는 것이다.

### 서명 검증 흐름

예를 들어 앨리스가 밥에게 메시지를 보낸다고 하자.

1. 앨리스가 메시지를 작성한다.
2. 메시지의 해시값을 구한다.
3. 그 해시값에 대해 개인키로 서명한다.
4. 메시지와 서명을 함께 밥에게 보낸다.
5. 밥은 받은 메시지의 해시를 다시 계산한다.
6. 밥은 앨리스의 공개키로 서명을 검증한다.
7. 검증이 성공하면 다음 두 가지를 알 수 있다.
    - 이 서명은 앨리스의 개인키로 생성되었다.
    - 메시지는 중간에 변조되지 않았다.

### 왜 해시에 서명할까

메시지 전체에 직접 서명하지 않고 보통 해시에 서명한다.

이유는 다음과 같다.

1. 효율적이다.
2. 서명 알고리즘은 정해진 크기의 입력에 잘 맞는다.
3. 메시지가 조금만 바뀌어도 해시가 달라져 무결성 검증에 유리하다.

## 3. 웹훅과 서명 검증

이 개념은 웹훅 보안에 매우 잘 맞는다.

웹훅은 외부 서비스가 우리 서버로 HTTP 요청을 보내는 구조다. 이때 우리 서버는 다음을 확인해야 한다.

1. 이 요청이 진짜 그 서비스가 보낸 요청인가
2. 요청 본문이 중간에 바뀌지 않았는가
3. 예전 요청을 누군가 다시 보내는 것은 아닌가

### 웹훅에서 많이 쓰는 방식

### 1) HMAC 기반 서명

가장 흔한 방식이다.

- 발신자와 수신자가 같은 secret을 공유한다.
- 발신자는 body를 기준으로 HMAC 값을 계산한다.
- 수신자는 같은 secret으로 다시 계산해서 비교한다.

이 방식은 비대칭키 기반은 아니지만, 웹훅 실무에서 매우 많이 사용된다.

### 2) 공개키 기반 디지털 서명

- 발신자는 개인키로 서명한다.
- 수신자는 공개키로 검증한다.

이 방식은 수신자가 비밀키를 공유받을 필요가 없다는 장점이 있다.

### 웹훅에서 raw body가 중요한 이유

서명 검증은 보통 파싱된 JSON 객체가 아니라 원본 요청 본문 기준으로 해야 한다.

예를 들어 다음 두 JSON은 의미는 같아 보이지만 문자열은 다르다.

```json
{"a":1,"b":2}
```

```json
{ "a": 1, "b": 2 }
```

서명은 보통 바이트 단위로 계산하므로 공백 하나만 달라도 결과가 달라질 수 있다. 그래서 raw body를 그대로 사용해야 한다.

## 4. 서명 검증이 없는 웹훅은 실제로 많은가

많다. 특히 다음 경우에 자주 보인다.

1. 사내에서 급하게 만든 내부 연동
2. 초기 프로토타입
3. 레거시 시스템
4. 단순히 IP 허용 목록만 두고 끝낸 구조

하지만 이런 구조는 좋은 설계라고 보기 어렵다. 특히 결제, 주문, 계정 상태 변경처럼 중요한 상태를 바꾸는 웹훅이라면 서명 검증이 없으면 위험하다.

## 5. IP만 검증하는 웹훅의 한계

처음 보면 허용된 IP에서만 받으면 되는 것 아닌가라고 생각하기 쉽다. 하지만 IP는 어디서 왔는지를 대략 알려줄 뿐, 누가 보냈는지와 내용이 안전한지는 보장하지 못한다.

### IP 검증이 보장하는 것

- 요청이 특정 네트워크 위치에서 왔다는 점

### IP 검증이 보장하지 못하는 것

- 진짜 웹훅 발신 애플리케이션이 보냈는가
- 요청 본문이 변조되지 않았는가
- 예전 요청의 재전송은 아닌가
- 허용된 인프라 내부가 침해되지 않았는가

즉, IP 검증은 보조 수단일 뿐 최종 신뢰 수단은 아니다.

## 6. 스푸핑은 왜 웹훅 공격에서 핵심이 아닌가

이 부분은 TCP를 이해하면 명확해진다.

웹훅은 보통 HTTP 또는 HTTPS 요청이고, 이는 TCP 연결 위에서 동작한다. 

TCP는 단순히 패킷 하나를 보내는 방식이 아니라 연결을 맺어야 한다.

### TCP 3-way handshake

정상 연결은 다음 순서로 이루어진다.

1. 클라이언트가 서버에 SYN 전송
2. 서버가 클라이언트에 SYN-ACK 응답
3. 클라이언트가 ACK 전송

이 과정을 마쳐야 연결이 성립한다.

### 단순 IP 스푸핑이 어려운 이유

공격자가 자신의 실제 IP가 아니라 허용된 IP로 출발지 주소를 위조해 SYN을 보냈다고 하자.

그러면 서버의 응답인 SYN-ACK는 공격자에게 가지 않고, 위조된 그 IP 쪽으로 간다. 공격자는 응답을 받지 못하므로 다음 ACK를 정상적으로 보낼 수 없고, TCP 연결을 완성할 수 없다.

즉, IP 헤더 위조 자체는 개념적으로 가능할 수 있어도, 웹훅처럼 HTTP 요청을 끝까지 정상적으로 성립시키는 데는 큰 제약이 있다.

### 그렇다면 왜 IP만으로는 부족한가

핵심은 현실적인 공격이 단순 스푸핑보다 다른 형태로 더 자주 일어나기 때문이다.

예를 들면 다음과 같다.

1. 허용된 인프라 내부 서버가 침해됨
2. 같은 NAT 또는 같은 프록시 뒤의 다른 시스템이 요청을 보냄
3. `X-Forwarded-For` 같은 헤더를 잘못 신뢰함
4. 정상 요청을 복사해서 다시 보내는 replay 공격

즉, 웹훅에서 중요한 것은 출발지 IP를 속일 수 있느냐보다, IP만으로 진짜 발신자와 요청 무결성을 판단할 수 있느냐이다. 답은 아니다.

## 7. nonce, eventId, timestamp는 왜 필요한가

이 값들은 서명 검증 자체를 위한 것이라기보다, 서명만으로 막지 못하는 replay와 duplicate 문제를 막기 위해 사용한다.

### 먼저 역할을 구분해야 한다

### 1) 서명 검증의 역할

- 진짜 발신자가 보냈는지 확인
- 본문이 변조되지 않았는지 확인

### 2) replay와 duplicate 방지의 역할

- 같은 요청을 다시 보내는 것을 막음
- 이미 처리한 이벤트를 다시 처리하지 않게 함

즉, 서명 검증이 통과했다고 해서 무조건 처리하면 안 되고, 그 다음에 중복 여부와 유효시간도 따져야 한다.

### timestamp

요청이 너무 오래되었는지 확인하는 값이다.

예를 들어 현재 시각 기준 5분 이상 지난 요청은 거부하는 식으로 사용한다. 이렇게 하면 예전 정상 요청을 누군가 다시 보내는 replay를 줄일 수 있다.

### nonce

요청마다 한 번만 쓰는 임의값이다.

수신자는 이미 본 nonce라면 거부한다. 주로 signed API 호출에서 많이 쓰이며, 웹훅에서는 eventId가 더 자주 사용된다.

### eventId

웹훅에서 가장 실무적으로 많이 쓰는 값이다.

각 이벤트에 고유 ID를 두고, 이미 처리한 eventId면 무시한다. 사실상 멱등키 역할을 한다.

예시:

```json
{
  "eventId": "evt_123",
  "type": "payment.completed",
  "orderId": "ord_1"
}
```

수신자는 `evt_123`을 이미 처리했는지 저장소에서 확인한 뒤, 처리 여부를 결정한다.

## 8. payload의 특정 값을 멱등키로 쓰면 되지 않나

맞다. 실무에서는 payload 안의 특정 값을 멱등키로 잡아 중복 처리 방지를 많이 한다.

하지만 주의할 점이 있다.

예를 들어 `orderId`만 멱등 기준으로 쓰면 다음 두 이벤트를 구분하지 못할 수 있다.

- `payment.completed` with `orderId=1`
- `payment.refunded` with `orderId=1`

따라서 단순 business key 하나만 쓰기보다, 보통 다음과 같은 키를 고려한다.

- `eventId`
- `provider + eventId`
- `eventType + providerEventId`
- `eventType + businessId + version`

즉, 비즈니스 식별자와 이벤트 식별자를 구분하는 것이 중요하다.

## 9. 서명 검증과 중복 확인은 같은 단계인가

보통은 분리해서 생각한다.

### 일반적인 처리 순서

1. HTTPS 확인
2. 보조적으로 IP allowlist 확인
3. timestamp 허용 범위 확인
4. 서명 검증
5. eventId 또는 nonce 중복 확인
6. 비즈니스 멱등 처리
7. 처리 성공 후 processed event 저장

여기서 중요한 점은 `timestamp`, `eventId`, `nonce` 같은 값도 서명 대상에 포함해야 한다는 것이다.

예를 들면 다음과 같다.

```
timestamp + "." + eventId + "." + rawBody
```

이렇게 해야 공격자가 timestamp나 eventId를 바꿔치기해도 서명 검증에서 걸러진다.

하지만 이미 처리한 eventId인지 확인하는 작업 자체는 여전히 별도의 저장소 조회 단계다.

즉,

- 서명 검증: 값이 위조되지 않았는지 확인
- 중복 확인: 이미 처리한 요청인지 확인

으로 역할이 나뉜다.

## 10. 멱등성과 replay 방지는 어떻게 다른가

비슷해 보이지만 관점이 다르다.

### 멱등성

같은 요청이 여러 번 와도 결과가 한 번만 반영되게 하는 것이다.

예:

- 같은 eventId면 DB 상태 변경을 한 번만 수행

### replay 방지

정상 요청을 누군가 복사해서 다시 보내는 것을 줄이는 것이다.

예:

- timestamp 검증
- nonce 재사용 거부

정리하면 다음과 같다.

- 멱등성은 비즈니스 처리 관점
- replay 방지는 보안 관점

실무에서는 둘 다 필요하다.

## 11. 실무적으로 권장되는 웹훅 방어 조합

최소한 다음 정도는 권장된다.

1. HTTPS 사용
2. IP allowlist는 보조 수단으로 사용
3. HMAC 또는 디지털 서명 검증
4. timestamp 허용 오차 검사
5. eventId 기반 중복 처리 방지
6. DB 또는 애플리케이션 레벨 멱등 처리

더 중요한 시스템이라면 다음도 고려할 수 있다.

1. mTLS
2. strict schema validation
3. unique constraint 기반 중복 방지
4. replay 저장소 TTL 관리
5. 상세 감사 로그

## 12. 최종 정리

### 비대칭키 사용 목적

1. 공개키 암호화와 개인키 복호화를 통한 기밀성 보장
2. 개인키 서명과 공개키 검증을 통한 신원 증명과 무결성 보장

### 웹훅 보안의 핵심

- 단순히 IP만 확인해서는 부족하다.
- 진짜 발신자 확인과 본문 무결성 확인을 위해 서명 검증이 필요하다.
- 정상 요청의 중복 처리와 replay를 막기 위해 eventId, nonce, timestamp가 필요하다.

### 가장 중요한 인식

- IP는 네트워크 위치를 보여줄 뿐이다.
- 서명은 요청의 진위와 무결성을 보여준다.
- eventId와 timestamp는 같은 요청의 재전송과 중복 처리를 제어한다.

즉, 웹훅 보안은 다음 세 층으로 이해하면 좋다.

1. 네트워크 수준 필터: IP allowlist
2. 요청 진위 확인: HMAC 또는 디지털 서명
3. 중복 및 replay 제어: eventId, nonce, timestamp, 멱등 처리

## 13. 한 줄 결론

웹훅에서 IP 검증은 보조 수단일 뿐이고, 실제로 신뢰할 수 있는 구조를 만들려면 서명 검증과 replay 및 중복 처리 방지를 함께 설계해야 한다.
